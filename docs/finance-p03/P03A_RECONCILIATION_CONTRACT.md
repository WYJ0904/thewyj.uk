# P03-A 权威修正、重归属与历史映射合同

本合同描述本隔离分支的实现。全部验证为合成账户；真实提供方语义适配器未取得，生产入口默认失败关闭。不能据此宣称真实微信、支付宝或银行通知已经支持自动更正。

## 证据与作用域

复用 Task21 原始事件、recognition、candidate、outbox、Task16 正式账目与 change feed。原事件和旧 ingest receipt 保留；新有效关联层不是第二套财务账本。

`payment.reconcile` 请求只包含 operation ID、动作、证据事件 ID、明确目标/解除别名列表、前驱事实版本、前驱修正 ID、预计正式账目 revision、proof ID。不接收原文、账户凭据、AI 判断或客户端 `verified` 标记。每组目标及解除列表分别最多8条。

默认 `verifyAuthority` 拒绝。内部可信适配器必须将完整 command digest、全部不可变源事件 digest、用户、发行方命名空间、提供方账户作用域、绝对操作版本语义及该次完成事实逐项绑定。单一 `completed=true` 不够；还须提供完成证据事件对应的 `completed_source_digests`。proof 不来自请求的自我声明。提供方账户仅保存不可逆作用域 hash，不保存真实卡号。真实模板/签名/操作版本语义未验证时保持 `provider_semantics_unverified`。

Android 还核对已知 UID/来源实例；同字面引用跨用户、发行方、提供方账户不允许自动关联。金额、时间、商户、文本相似和 AI 置信度均不参与证明交易相同。

## 已实现的动作

| 动作 | 条件与结果 |
| --- | --- |
| REPLACE | 同作用域、家族、角色及独立操作引用，事实版本必须紧接前驱；把权威绝对 Capture/Refund 金额应用到原正式账目 ID，记录修正前后状态及 change feed |
| MAP | 明确证明一组弱候选属于同一操作；无账目时创建一笔，有唯一自动账目时保留其 ID；多个正式账目、多个可能匹配或缺证明时隔离 |
| REASSIGN | 权威证明原家族/操作关联有误；保留原正式账目 ID，原子更新有效关联，并同时检查旧、新家族的退款和解除约束 |
| REVOKE | 必须是明确完成、独立引用的全额退款/冲正事实；保留原正金额支出，另建正金额退款，净额归零。遵守 Task16 `amount_minor>0` 合同，不把原账改成0或删除 |
| detach_event_ids | 只解除不拥有自身原始账目的错误别名；原事件、原别名及旧回执保存，当前关联转为待核实，原正式账目继续存在 |

解除的别名在原关系未知时版本归0、状态 REVIEW_REQUIRED；之后取得同账户、同发行方的精确独立 Capture 证明，可以重新 MAP 成独立账目。实测原90与新80合计170；没有证明时仍只有原正式账与待核实项。Android 新增逐别名覆盖及独立 review 记录，避免为解除一个投递而移动整条 recognition。

两条独立 Capture 即使同金额同时间仍是两笔；同操作的精确重复只产生一笔。多个已经存在的正式账目不自动合并。旧弱账目还须证明自动创建来源；手动确认标记或来源不明分别进入 `user_decision_conflict` / `legacy_ledger_origin_unproven`。

## 用户决定与版本保护

现有 Task16 revision、status、source_kind、reconciliation_state、原始创建元数据及候选 edits 保留。用户编辑、删除、恢复、合并/拆分后的 revision 不冒充系统修正。系统后续修正只能沿已接受的自身日志继续；不静默覆盖人工金额、商户或备注，不恢复用户删除的账目。新增候选/hint 显式确认标记，兼容检查旧 `verified-on-device` / `pending-hint` 创建标记。

正式账本与源清算投影职责分离。用户决定导致两者数值不同是审计冲突，不是拿投影覆盖正式账本的理由。旧修正回执遇到之后的用户 revision，只返回待核实，不再回放旧金额。

每个旧别名读取主 recognition 的最新接受版本；各别名的原始事件及当时关联快照保留。新增可失败测试曾复现第三版95后旧别名仍读第二版90，已修正并验证旧 ACK 不会改回90。

## 事务、余额与重放

D1 在同一 batch 内执行账户版本 fence、源状态/关联 CAS、用户决定检查、有效关联更新、旧新家族余额 CHECK、正式账目/change feed、修正日志及审计记录。与普通退款共享有效事件视图；并发请求不能分别通过 JavaScript 检查后超额。原授权不入支出，金额/币种、累计退款、解除额及安全整数约束保留。修正导致已接受退款或解除不再成立时整体回滚并待核实。

完整 before image 存入新修正日志。旧 Task16 审计格上限12 KB，故保存日志 operation ID、完整快照 SHA-256、源事件 ID 与原正式账目摘要；不截断、丢弃完整证据。八候选大快照回归覆盖该边界。

Android 先持久化 staged 日志，再恢复到原磁盘 outbox；不先改变金额。HTTP503保留原 operation ID 和原请求。只有账户、payload digest、目标集合、规范 ID、事实金额/币种/版本匹配的已提交回执，才在 Room 事务内更新原 booking、关联与候选，然后移除队列。数据库提交后进程退出而队列未删，重放不重复入账。普通同 ID ACK 的时间戳/运输状态变化不属于用户资金修改；金额、ID、编辑及决定仍参与 CAS。

本地状态改变或回执不一致时保留日志、候选和队列，沿既有拒绝次数门禁停止反复上传。新、未证明的更正后引用别名需重新提供权威关系，不借旧原始金额创建第二笔支出。Task16 旧 raw 写入口也拒绝绕过已更正身份；保留原客户端请求待核实。

该保护位于共用正式记账函数，覆盖缺少可选新字段的旧 structured 请求和 hint 路径。已证明的旧来源可通过原单事件 hint 请求取得实际持久化的 Event receipt（新增 `operation_results`），不伪造 hint 行；未知更正引用拒绝自动处理。更正事件的多条 hint 批次要求拆为原单事件请求。已接受的 AUTHORIZE/RELEASE/EXPIRED 控制事实不能被 MAP 或 REASSIGN 消耗成 Capture 别名，以免丢失原授权额度。

## 明确边界

- C005 原80账不变，90缺独立操作证据时继续待核实，冻结170目标仍红；不虚构解除额。
- C007 冻结170目标不变；缺引用时0正式账不能标 PASS。独立受证 Capture 的170路径另列测试，未替换原样本。
- 授权/Release 控制事件的版本更正不在正式账目修正动作中自动应用；原基础生命周期合同保留，不把这些未支持的修订解释成正式支出。
- 实际提供方账户、版本、前驱、完成事实及取消/退款语义须先有真实可核对的来源合同。当前只有合成验证器，真实自动修正仍 BLOCKED。
- P04 币种展示/FX、P05 OCR 语义、P06 AI 与真实业务门禁不因本轮合成 PASS 自动关闭。
